# fingertip-mcp

`fingertip-mcp` lets an agent — Claude Code, or any MCP client — do manual verification itself: read the screen, tap, type, scroll, screenshot, relaunch — on a simulator or a Mac app, through the same `ScreenInspector` / `ScreenDriver` the app uses. Claude is the one deciding here; Jev only comes in through `run_instruction`.

Tools: `list_targets`, `connect` (`udid` or `bundle_id` [+ `app_path`, `test`]), `end_test` (`passed` [+ `notes`]), `read_screen` (`full` for uncut texts, `skeleton` for region counts, `region` for one region, `window` to choose a Mac window), `list_windows`, `bring_to_front` (`window`), `wait_for` (`text` [+ `tap` / `gone`, `timeout`]), `tap` (`alias` as `L:N`, or `x`,`y`), `select` (`alias`, `option`), `set_value` (`alias`, `value`), `toggle` (`alias`), `type_text`, `erase_text`, `submit` (Return in the focused field), `scroll`, `swipe`, `press_button`, `screenshot`, `start_recording` / `stop_recording`, `relaunch_app`, `terminate_app`, `run_instruction` (delegates a whole run to `JevAgent`, writes the usual JSONL + screenshots).

## Design

- **Waiting happens in the server, not in Claude.** A Claude turn takes seconds; a read takes under 0.1 s on macOS. Anything short-lived — an approval card that lasts 30 s — is missed if Claude has to notice it, read again and then tap. `wait_for` polls every 0.25 s and, with `tap: true`, taps the moment the element appears. To tap, only an exact match or a non-text element counts: the word «Aprobar» is usually also in the message body, which exists before the card, and a substring match tapped that text in the first test.
- **The outline is cut for size.** Every action returns the whole screen, so texts are flattened to one line and cut at 100 characters with their full length (`… (986 characters)`); `read_screen` with `full: true` returns them whole. `wait_for` matches against the full text. `MacDriver` also drops exact duplicates (same role, label, text, id and frame) — SwiftUI exposes many texts twice — so they do not reach Jev's Choice either.
- **Every action returns the new screen.** It goes through `ScreenInspector.perform`, which waits and re-reads, so the aliases in the reply are the valid ones.
- **Every Mac action says how it was delivered.** The reply has a `Delivery:` line with each strategy the driver tried and its outcome: `not_delivered` (the app refused it), `no_effect` (it took it and nothing it should change changed), `delivered` (took it, nothing to check) or `verified` (took it and the change was read back). `AXPress no effect → AXSelected (Row) verified` is a press that selected nothing, followed by a selection that worked. See `docs/macos.md` for what each step checks. It is text only, like every successful reply: Claude Code shows `structuredContent` *instead of* the text when a result has both, so a success with structured content would lose the screen. Only errors carry it. The simulator reports nothing: sim-use only says whether it ran.
- **A Mac app with several windows needs a choice.** The MCP connects with `requireWindowChoice`: with two or more standard, non-minimized windows and none chosen, reads fail with `ambiguous_window`, which lists them (`#4312 «Downloads»`). Windows on another desktop count too and are listed as such; choosing one that is not the app's focused window is `window_on_other_space`, since AX cannot reach it from here (`docs/macos.md`). `connect` still connects and returns that error. `list_windows` shows number, title, frame and which is focused or chosen; `read_screen` with `window: <number>` chooses one and reads it, and the choice holds for every later tool until that window closes (`window_gone`) or the app relaunches. A modal dialog of the app is read instead while it is up. `run_instruction` goes through the same driver, so on such an app it fails with `ambiguous_window` until a window is chosen.
- **`bring_to_front` is off until the user turns it on.** It activates the app and can switch the desktop the user is looking at, so it runs only with Settings → General → Windows on in the Fingertip app (`allowsBringToFront` in `settings.json`, read on every call: no reconnect). Off, it fails with `bring_to_front_disabled`. On, it brings `window` (else the chosen one, else the only one: several and none chosen is `ambiguous_window`) to the front, chooses it and returns its reading; a window it could not get in front within 2 s is `not_brought_forward`. How it reaches a window on another desktop is in `docs/macos.md`. It is the way out of `window_on_other_space`. Like the sensitive-app block, there is no tool argument for the setting.
- **`select`, `set_value` and `toggle` are macOS only** and are checked against the caller's reading like `tap`. `select` opens a pop-up or menu button, picks the item by name (case and accents ignored; a unique partial match also counts) and reads the control back; with a menu already open it refuses (`menu_already_open`), and with no such item it cancels the menu and lists the options (`option_not_found`). `set_value` writes text through the field editor, a date (`yyyy-MM-dd HH:mm`, `yyyy-MM-dd` or `HH:mm`, local) or a number, then reads it back (`no_effect` if it did not take, `not_settable` for a read-only element). `toggle` flips a checkbox, radio or switch and confirms the flip. On the simulator they fail with `unsupported`. The status toast never shows a `set_value` value, as with typed text.
- **Aliases carry their reading: `@L:N`.** `ScreenInspector.reading` only moves when the element list changes (type, region, identifier, label, text — not bounds), and the last 20 readings are kept. `tap` with `L:N` re-reads first and taps only if element N and everything before it are unchanged since reading L; otherwise it returns `screen_changed` with the current screen. Aliases are positions in the flattened list, so only what comes before N can make it point elsewhere: a streaming reply below the target does not invalidate it. A bare `N` is rejected. On iOS the status bar is in `Top`, before everything else, so a minute change on the clock invalidates older aliases; the rejection already carries the new ones.
- **Dense screens are read by region.** `read_screen` with `skeleton: true` lists each region with its element count; with `region` it lists only that region and keeps it as the focus, so later actions also show only it, until a `read_screen` without `region`. Past 150 elements the outline suggests this. On macOS every `AXScrollArea` is a region of its own (named from its AX description, title or identifier, or the list inside it; `_NS:` identifiers are skipped), so a sidebar and a content view read apart.
- **Errors are coded.** Every failure starts with `Error <code> · retry_safe: <bool>` and carries the same in `structuredContent.error` (`code`, `retry_safe`, `message`). `retry_safe` means re-reading and trying again cannot do harm and may succeed (`screen_changed`, `unknown_alias`, `stale_alias`, `timed_out`, `no_window`, `process_timed_out` on a read…); a failed AX action is safe only when its AX error says it never ran (unsupported, invalid element); a timeout, a `no_effect`, a blocked app or a missing permission are not. A retry-safe failure of an action comes with the current screen. The codes live next to each error type (`MacDriverError`, `SimUseError`, `SimctlError`, `SubprocessTimeout`, `JevError`, `InspectorError`, `JevAgentError`, `ToolError`).
- **Auto-connect**: with no `connect` and exactly one booted simulator, the first tool connects to it.
- **Screenshots**: inline as JPEG with the long side at 1280 px, full PNG in the folder chosen in the Fingertip app (Settings → Captures), `$TMPDIR/fingertip-mcp/` by default, with its path in the reply. The setting is read on every call.
- **Recording**: `start_recording` / `stop_recording` produce a `.mov` (h264, no audio) in the folder chosen in the Fingertip app (Settings → Captures → MCP Recordings), `$TMPDIR/fingertip-mcp/recordings/` by default, with its path in the reply. One at a time per driver: a second start is `already_recording`, a stop with none is `not_recording`. The simulator goes through `simctl io recordVideo`, which only emits frames when the screen changes, so a still screen at the end is not in the duration. A Mac app records its window with `SCRecordingOutput` (at the window's display scale), in a `fingertip-mcp record` child (see `docs/macos.md`), which also stops if the server dies, SIGKILL included. `disconnect` (also the one `connect` does when switching devices, which names the closed file in its reply), closing the server (stdin EOF) and SIGTERM/SIGINT/SIGHUP stop a recording so the file is closed; a SIGKILL of the server cannot for the simulator.
- **Tests**: `connect` with `test: "<name>"` opens a test; without it nothing is written, because fingertip is also used to just operate apps. A test is a folder under `~/Library/Application Support/Fingertip/tests/<date>-<name>/` (a constant, not a setting): `test.json` (name, target, start, end, verdict `passed`/`failed`/`none`, notes, `recording_error` when there is no video), `trace.jsonl` (one line per tool call: tool, arguments with typed text redacted as in the toast and Jev's log — `type_text`/`set_value` keep only the length, `run_instruction` its quoted texts as `[text]`, and every later reply that echoes them is redacted too —, the reply's text, the error code, ms, and the screen after the call in `screens/`, deduplicated by hash), `recording.mov` (started by the `connect`, it takes the one recording slot, so `start_recording`/`stop_recording` answer `test_in_progress`) and `jev/` (`run_instruction` logs while the test is open). `end_test` closes it with a verdict; a new `connect`, closing the server and the signals above close it with verdict `none`. `end_test` with no test open is `no_test`. The app's "Tests…" menu item opens a read-only window over this folder: the tests newest first with their verdict, and for one test its notes, the video and each step with the screen after it.
- No MCP SDK: the needed surface is four methods (`initialize`, `tools/list`, `tools/call`, `ping`), and the binary keeps zero dependencies.
- **Permissions** for Mac apps belong to the *responsible* process — the terminal running Claude Code (or whichever client launched the server), not `fingertip-mcp`. The simulator needs none.
- **Sensitive Mac apps are blocked by default.** Everything the server reads off a screen reaches Claude as text, so an instruction hidden in a web page or an email could steer it into connecting to a terminal and typing a command. `connect`, `relaunch_app`, `terminate_app` and `run_instruction` refuse terminals, editors with a terminal (VS Code and its forks, Cursor, Windsurf, Zed, Nova, JetBrains IDEs), other agents' apps (Claude, Codex, ChatGPT), Script Editor / Automator / Shortcuts and launchers that run scripts, System Settings, password managers, and Fingertip itself, whose Settings holds the switch that lifts the block (`BlockedApps` in `FingertipCore`); `list_targets` marks them `blocked`. The app's Settings → Security lists them: each one can be allowed on its own, and the user can add more. Those choices live in the shared `settings.json`. Added blocks are read on every check (`connect`, `relaunch_app`, `terminate_app`, `run_instruction`; an app already connected stays connected); allowed apps and removed blocks only at launch, so lifting anything takes `/mcp`: the file can be edited through any unblocked text editor, and read live, an injected instruction could unblock a terminal mid-session. An app is blocked while any entry matching it is (allowing the JetBrains prefix does not let through an IDE added on its own). Fingertip itself can't be allowed on its own. God mode lifts the whole block, Fingertip included: it is `-e FINGERTIP_UNRESTRICTED=1` at registration, set by hand or with the app's "God mode" switch, which re-registers the server. Never as a tool argument: the same injected instruction could pass it. For a one-off, set `mcp__fingertip__connect` to ask in Claude Code's permissions.
- **Do not drive the same simulator from the app and the MCP at once**: sim-use keeps one `@N` cache per UDID on disk, and each side's `ui` overwrites the other's.
- `run_instruction` needs `TYPESAFE_API_KEY` in the server's environment (`claude mcp add … -e TYPESAFE_API_KEY=…`, or exported in the shell that starts Claude Code).

## Registration

Two registrations share the name `fingertip`, and Claude Code uses the narrower scope:

- **User scope → the installed app.** Fingertip's Settings → Claude Code → Install / Update runs `claude mcp add --scope user` with the `fingertip-mcp` bundled in the app it is running from, so press it from `/Applications/Fingertip.app`: pressed from an app launched by Xcode, it registers a path inside DerivedData, and later updates to the installed app no longer reach Claude Code. A Sparkle update replaces the bundled binary in place, so it only needs `/mcp` → reconnect.
- **Local scope → the development build**, in this repo only, so sessions here run the code being changed. Not in a shared `.mcp.json`, because the command is an absolute path into `.build/`:

```bash
swift build -c release
claude mcp add --scope local fingertip -- "$PWD/.build/release/fingertip-mcp"
```

Rebuild in release after changing the package; Claude Code picks the new binary up on its next session (or `/mcp` → reconnect). A running session keeps the binary it launched until then. `claude mcp get fingertip` shows which registration a directory gets.

### Other MCP clients

The server is plain MCP over stdio (`initialize`, `tools/list`, `tools/call`, `ping`), so any client that launches a local stdio server can use it. The command is the binary with no arguments: `/Applications/Fingertip.app/Contents/Resources/fingertip-mcp` from the app, or `.build/release/fingertip-mcp` from source. `FINGERTIP_UNRESTRICTED` and `TYPESAFE_API_KEY` go in the client's `env` for the server.

Codex CLI (`~/.codex/config.toml`):

```toml
[mcp_servers.fingertip]
command = "/Applications/Fingertip.app/Contents/Resources/fingertip-mcp"
default_tools_approval_mode = "approve"   # optional: without it every call asks
```

Clients that use the common `mcpServers` JSON (Cursor, Claude Desktop, Gemini CLI, VS Code with its own `servers` key):

```json
{ "mcpServers": { "fingertip": { "command": "/Applications/Fingertip.app/Contents/Resources/fingertip-mcp" } } }
```

What changes outside Claude Code:

- **Registration is by hand.** The Fingertip app only registers the server in Claude Code.
- **Mac permissions** go to the client's process: the terminal that runs a CLI client, or the client app itself (Cursor, Claude Desktop). The simulator needs none.
- **The status toast has no `Done`.** The end of a turn comes from a Claude Code `Stop` hook; without it the toast fades 45 s after the last event. The edge indicator and the pointer work the same.
- **Blocked apps** stay blocked, and the one-off way around it is the client's own approval for `connect`, not Claude Code's permissions.
- Some error texts still name Claude Code (`/mcp`, `claude mcp add`, "the terminal running Claude Code"); the fix they describe applies to any client.

Verified on 2026-11-04 with Codex CLI 0.166.0 against `.build/release/fingertip-mcp`: `list_targets`, `connect` to Calculator, `read_screen`, and two `tap`s by alias (the field went 5 → 57 → 0, `Entrega: AXPress entregado`), with the permissions of the terminal running Codex. Not verified: the simulator through another client (`connect` failed here with `sim_use_failed` also over raw JSON-RPC, so it was the simulator, not the client), and Cursor, Claude Desktop and Gemini CLI.

## Status toast and the Stop hook

With the Fingertip menu-bar app running, every tool call sends an `OverlayEvent.status` over the `ActivityBeacon` socket when it starts (`Tapping «Wallpaper»`, `Waiting for «Applications»`) and when it ends (fine, or failed with its error code), and `JevAgent` sends one per step (what it chose and with what confidence, or why it stopped). The app shows them in a toast above the bottom edge of the screen.

The server only sees tool calls, so "thinking" is inferred: 0.8 s after a call finishes fine, the toast says `Thinking…`. The end of a turn is invisible to it; a Claude Code `Stop` hook supplies it:

```json
"Stop": [{ "hooks": [{ "type": "command", "timeout": 3,
  "command": "printf '{\"turn\":{\"ended\":true,\"owner\":%d}}\\n' \"$PPID\" | nc -U -w 1 \"$HOME/Library/Application Support/fingertip/overlay.sock\" >/dev/null 2>&1 || true" }] }]
```

The hook fires for every Claude Code session. `$PPID` in the hook is the Claude Code process, the same one that spawned the MCP, which sends it as the `owner` of its `OverlayEvent.session`; the app shows `Done` only while its toast is up and only for the session the toast last spoke for, so a session that never used fingertip shows nothing and one that ends doesn't cut off another that is still working. A hook without `owner` (the older form) still ends any toast that is up. Without the hook, the toast fades 45 s after the last event. Connections that only drop an event, like this one, don't send `OverlayEvent.session` and so don't light the edge indicator.

**The edge indicator means fingertip is acting, not that it is connected.** The MCP opens its session connection when a tool call starts (once a device is connected) and closes it 30 s after the last call ends (`ActivityBeacon.beginActivity` / `endActivity`); the next call reopens it. The app also puts a session to sleep when the Stop hook reports the end of its owner's turn, and wakes it with that session's next status or pointer event; a hook without `owner` puts every session to sleep. Before this, the connection stayed open from the first `connect` until the Claude Code session closed, so the edge glowed for the whole session.
