# fingertip-mcp

`fingertip-mcp` lets Claude Code do manual verification itself: read the screen, tap, type, scroll, screenshot, relaunch — on a simulator or a Mac app, through the same `ScreenInspector` / `ScreenDriver` the app uses. Claude is the one deciding here; Jev only comes in through `run_instruction`.

Tools: `list_targets`, `connect` (`udid` or `bundle_id` [+ `app_path`]), `read_screen` (`full` for uncut texts, `skeleton` for region counts, `region` for one region, `window` to choose a Mac window), `list_windows`, `wait_for` (`text` [+ `tap` / `gone`, `timeout`]), `tap` (`alias` as `L:N`, or `x`,`y`), `select` (`alias`, `option`), `set_value` (`alias`, `value`), `toggle` (`alias`), `type_text`, `erase_text`, `submit` (Return in the focused field), `scroll`, `swipe`, `press_button`, `screenshot`, `start_recording` / `stop_recording`, `relaunch_app`, `terminate_app`, `run_instruction` (delegates a whole run to `JevAgent`, writes the usual JSONL + screenshots).

## Design

- **Waiting happens in the server, not in Claude.** A Claude turn takes seconds; a read takes under 0.1 s on macOS. Anything short-lived — an approval card that lasts 30 s — is missed if Claude has to notice it, read again and then tap. `wait_for` polls every 0.25 s and, with `tap: true`, taps the moment the element appears. To tap, only an exact match or a non-text element counts: the word «Aprobar» is usually also in the message body, which exists before the card, and a substring match tapped that text in the first test.
- **The outline is cut for size.** Every action returns the whole screen, so texts are flattened to one line and cut at 100 characters with their full length (`… (986 caracteres)`); `read_screen` with `full: true` returns them whole. `wait_for` matches against the full text. `MacDriver` also drops exact duplicates (same role, label, text, id and frame) — SwiftUI exposes many texts twice — so they do not reach Jev's Choice either.
- **Every action returns the new screen.** It goes through `ScreenInspector.perform`, which waits and re-reads, so the aliases in the reply are the valid ones.
- **Every Mac action says how it was delivered.** The reply has an `Entrega:` line with each strategy the driver tried and its outcome: `not_delivered` (the app refused it), `no_effect` (it took it and nothing it should change changed), `delivered` (took it, nothing to check) or `verified` (took it and the change was read back). `AXPress sin efecto → AXSelected (Row) verificado` is a press that selected nothing, followed by a selection that worked. See `docs/macos.md` for what each step checks. It is text only, like every successful reply: Claude Code shows `structuredContent` *instead of* the text when a result has both, so a success with structured content would lose the screen. Only errors carry it. The simulator reports nothing: sim-use only says whether it ran.
- **A Mac app with several windows needs a choice.** The MCP connects with `requireWindowChoice`: with two or more standard, non-minimized windows and none chosen, reads fail with `ambiguous_window`, which lists them (`#4312 «Downloads»`). Windows on another desktop count too and are listed as such; choosing one that is not the app's focused window is `window_on_other_space`, since AX cannot reach it from here (`docs/macos.md`). `connect` still connects and returns that error. `list_windows` shows number, title, frame and which is focused or chosen; `read_screen` with `window: <number>` chooses one and reads it, and the choice holds for every later tool until that window closes (`window_gone`) or the app relaunches. A modal dialog of the app is read instead while it is up. `run_instruction` goes through the same driver, so on such an app it fails with `ambiguous_window` until a window is chosen.
- **`select`, `set_value` and `toggle` are macOS only** and are checked against the caller's reading like `tap`. `select` opens a pop-up or menu button, picks the item by name (case and accents ignored; a unique partial match also counts) and reads the control back; with a menu already open it refuses (`menu_already_open`), and with no such item it cancels the menu and lists the options (`option_not_found`). `set_value` writes text through the field editor, a date (`yyyy-MM-dd HH:mm`, `yyyy-MM-dd` or `HH:mm`, local) or a number, then reads it back (`no_effect` if it did not take, `not_settable` for a read-only element). `toggle` flips a checkbox, radio or switch and confirms the flip. On the simulator they fail with `unsupported`. The status toast never shows a `set_value` value, as with typed text.
- **Aliases carry their reading: `@L:N`.** `ScreenInspector.reading` only moves when the element list changes (type, region, identifier, label, text — not bounds), and the last 20 readings are kept. `tap` with `L:N` re-reads first and taps only if element N and everything before it are unchanged since reading L; otherwise it returns `screen_changed` with the current screen. Aliases are positions in the flattened list, so only what comes before N can make it point elsewhere: a streaming reply below the target does not invalidate it. A bare `N` is rejected. On iOS the status bar is in `Top`, before everything else, so a minute change on the clock invalidates older aliases; the rejection already carries the new ones.
- **Dense screens are read by region.** `read_screen` with `skeleton: true` lists each region with its element count; with `region` it lists only that region and keeps it as the focus, so later actions also show only it, until a `read_screen` without `region`. Past 150 elements the outline suggests this. On macOS every `AXScrollArea` is a region of its own (named from its AX description, title or identifier, or the list inside it; `_NS:` identifiers are skipped), so a sidebar and a content view read apart.
- **Errors are coded.** Every failure starts with `Error <code> · retry_safe: <bool>` and carries the same in `structuredContent.error` (`code`, `retry_safe`, `message`). `retry_safe` means re-reading and trying again cannot do harm and may succeed (`screen_changed`, `unknown_alias`, `stale_alias`, `timed_out`, `no_window`, `process_timed_out` on a read…); a failed AX action is safe only when its AX error says it never ran (unsupported, invalid element); a timeout, a `no_effect`, a blocked app or a missing permission are not. A retry-safe failure of an action comes with the current screen. The codes live next to each error type (`MacDriverError`, `SimUseError`, `SimctlError`, `SubprocessTimeout`, `JevError`, `InspectorError`, `JevAgentError`, `ToolError`).
- **Auto-connect**: with no `connect` and exactly one booted simulator, the first tool connects to it.
- **Screenshots**: inline as JPEG with the long side at 1280 px, full PNG in the folder chosen in the Fingertip app (Settings → Capturas), `$TMPDIR/fingertip-mcp/` by default, with its path in the reply. The setting is read on every call.
- **Recording**: `start_recording` / `stop_recording` produce a `.mov` (h264, no audio) in the folder chosen in the Fingertip app (Settings → Capturas → Grabaciones), `$TMPDIR/fingertip-mcp/recordings/` by default, with its path in the reply. One at a time per driver: a second start is `already_recording`, a stop with none is `not_recording`. The simulator goes through `simctl io recordVideo`, which only emits frames when the screen changes, so a still screen at the end is not in the duration. A Mac app records its window with `SCRecordingOutput` (at the window's display scale). `disconnect` (also the one `connect` does when switching devices, which names the closed file in its reply), closing the server (stdin EOF) and SIGTERM/SIGINT/SIGHUP stop a recording so the file is closed; a SIGKILL of the server cannot.
- No MCP SDK: the needed surface is four methods (`initialize`, `tools/list`, `tools/call`, `ping`), and the binary keeps zero dependencies.
- **Permissions** for Mac apps belong to the *responsible* process — the terminal running Claude Code, not `fingertip-mcp`. The simulator needs none.
- **Sensitive Mac apps are blocked by default.** Everything the server reads off a screen reaches Claude as text, so an instruction hidden in a web page or an email could steer it into connecting to a terminal and typing a command. `connect`, `relaunch_app`, `terminate_app` and `run_instruction` refuse terminals, editors with a terminal (VS Code and its forks, Cursor, Windsurf, Zed, Nova, JetBrains IDEs), Claude, Script Editor / Automator / Shortcuts and launchers that run scripts, System Settings, and password managers (`Session.blockedApps`, plus the `com.jetbrains.` prefix); `list_targets` marks them `bloqueada`. Only the user lifts it, by registering the server with `-e FINGERTIP_UNRESTRICTED=1`. Never as a tool argument: the same injected instruction could pass it. For a one-off, set `mcp__fingertip__connect` to ask in Claude Code's permissions.
- **Do not drive the same simulator from the app and the MCP at once**: sim-use keeps one `@N` cache per UDID on disk, and each side's `ui` overwrites the other's.
- `run_instruction` needs `TYPESAFE_API_KEY` in the server's environment (`claude mcp add … -e TYPESAFE_API_KEY=…`, or exported in the shell that starts Claude Code).

## Registration

Registered at user scope, so it is available from the repo of whatever app is under test; not in a shared `.mcp.json`, because the command is an absolute path into `.build/`:

```bash
swift build -c release
claude mcp add --scope user fingertip -- "$PWD/.build/release/fingertip-mcp"
```

Rebuild in release after changing the package; Claude Code picks the new binary up on its next session (or `/mcp` → reconnect).

## Status toast and the Stop hook

With the Fingertip menu-bar app running, every tool call sends an `OverlayEvent.status` over the `ActivityBeacon` socket when it starts (`Tocando «Wallpaper»`, `Esperando «Applications»`) and when it ends (fine, or failed with its error code), and `JevAgent` sends one per step (what it chose and with what confidence, or why it stopped). The app shows them in a toast above the bottom edge of the screen.

The server only sees tool calls, so "thinking" is inferred: 0.8 s after a call finishes fine, the toast says `Pensando…`. The end of a turn is invisible to it; a Claude Code `Stop` hook supplies it:

```json
"Stop": [{ "hooks": [{ "type": "command", "timeout": 3,
  "command": "printf '{\"turn\":{\"ended\":true,\"owner\":%d}}\\n' \"$PPID\" | nc -U -w 1 \"$HOME/Library/Application Support/fingertip/overlay.sock\" >/dev/null 2>&1 || true" }] }]
```

The hook fires for every Claude Code session. `$PPID` in the hook is the Claude Code process, the same one that spawned the MCP, which sends it as the `owner` of its `OverlayEvent.session`; the app shows `Listo` only while its toast is up and only for the session the toast last spoke for, so a session that never used fingertip shows nothing and one that ends doesn't cut off another that is still working. A hook without `owner` (the older form) still ends any toast that is up. Without the hook, the toast fades 45 s after the last event. Connections that only drop an event, like this one, don't send `OverlayEvent.session` and so don't light the edge indicator.

**The edge indicator means fingertip is acting, not that it is connected.** The MCP opens its session connection when a tool call starts (once a device is connected) and closes it 30 s after the last call ends (`ActivityBeacon.beginActivity` / `endActivity`); the next call reopens it. The app also puts a session to sleep when the Stop hook reports the end of its owner's turn, and wakes it with that session's next status or pointer event; a hook without `owner` puts every session to sleep. Before this, the connection stayed open from the first `connect` until the Claude Code session closed, so the edge glowed for the whole session.
