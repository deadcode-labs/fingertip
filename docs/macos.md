# Driving macOS apps

`MacDriver` talks to the target app directly through `AXUIElement` (read and act) and ScreenCaptureKit (pixels): no external process, no XCTest. Everything except the click fallback works **with the app in the background and without moving the cursor**, so the Mac stays usable during a run.

The app needs **Accessibility** (hard requirement, `preflight()` prompts for it) and **Screen Recording** (only screenshots, recordings and the run screenshots need it). Launched by Claude Code as a child of a terminal, TCC attributes them to the terminal.

## Measured behaviour

macOS 27, Calculator and System Settings:

- **There is a tree**, unlike sim-use, but it is flattened the same way: candidates are a list, and the UI groups by region (`Ventana` / `Toolbar` / `Hoja` / `Menú`, and one per `AXScrollArea`, named from its AX description, title or identifier or from the list inside it — Finder reads as `sidebar` and `icon view`). Containers (`AXGroup`, `AXScrollArea`, `AXRow`, `AXCell`, …) are walked but not offered; they are dropped in the driver, not in `UIElement.isActionable`, because `Cell` on iOS is exactly what gets tapped.
- **Read attributes in one batch** (`AXUIElementCopyMultipleAttributeValues`). One call per attribute took 1.7 s for System Settings' 212 nodes; batched, a read is 40–90 ms cold and under 10 ms warm.
- **Visibility comes from frames.** A 0×0 subtree is a closed menu or a collapsed row; anything outside the window, or outside an enclosing `AXScrollArea`, is scrolled out of view. Both are pruned. Off-screen rows keep their real positions, which is what makes the content height measurable.
- **Search fields often have no title, description or identifier** — only `AXPlaceholderValue`. Without reading it they fail `hasIdentity` and vanish.
- **SwiftUI `Form` controls are named from outside.** A `Picker("Agente")`, `DatePicker("Hora")` or `Toggle("Yolo")` has no title or description; its name is the `AXStaticText` pointed to by `AXTitleUIElement`. The driver reads it only for nodes with no name of their own. State comes from `AXValue`: the chosen option of a pop-up, the date of an `AXDateTimeArea` (`yyyy-MM-dd HH:mm`, local), and 0/1 for checkboxes, radios and switches (`UIElement.isChecked`, `[marcado]`/`[desmarcado]` in the MCP outline).
- **A sheet is the focused window, and reading stays inside it**: frames and `screenSize` are relative to the sheet. ScreenCaptureKit lists the sheet as its own window, but capturing it returns the *parent* window squeezed into the sheet's size; `screenshot` captures the parent (which draws the sheet on top) and crops to the sheet, so the image and the read share one coordinate space.
- **A stale alias is an error, not a fallback.** `ScreenInspector` checks first that nothing up to the element changed since the caller's reading (`screen_changed`). If the element itself went away in between, the cached `AXUIElement` reads back with no role; `tap` throws `staleAlias` instead of trying the ancestors and a click.
- **An AX call's success says the app took it, not that it did anything** (`MacActions.swift`). `AXPress` on Calculator's "Mode" returns success and opens nothing; `AXSelected` on a Reminders section row returns success and selects nothing. So each step of an action reports a `DeliveryStep`: `notDelivered`, `noEffect`, `delivered` (nothing to check) or `verified` (read back), and only the first two let the next step run. The MCP prints them as the `Entrega:` line.
- **"Unsupported" is not trusted for an advertised action.** Finder's sidebar cell advertises `AXOpen`, answers `-25205` (`attributeUnsupported`) and navigates anyway, 130 ms later; a Reminders cell answers the same to `AXPress` and does nothing. When an element advertised the action and answers either "unsupported" code, the driver compares the window against the reading taken just before (`readingFingerprint`: the same walk as a read, so a change a read would show counts) for up to 600 ms. Advertised actions are read *before* acting: Finder rebuilds its sidebar on navigating and the cell is gone afterwards.
- **Tapping a sidebar text navigates through the cell's `AXOpen`; selecting the row does not.** Measured on Finder's sidebar: `AXSelected` on the row highlights it without changing the folder, `AXOpen` on its `AXCell` changes the folder.
- **Tap order**: text input → `AXFocused`; a pop-up → open its menu (below); the element's `AXPress` (inside a row, read back: the row selected is `verified`, the window changed is `delivered`, neither is `noEffect`); its `AXOpen`; a child with the same name that has `AXPress`/`AXOpen` (SwiftUI exposes one control twice; another control of the row is never pressed for it); then up to four ancestors, each trying `AXPress`, `AXOpen` and, on an `AXRow`, `AXSelected` read back; only then a real `CGEvent` click, which brings the app to the front first.
- **Menu-bar menus are never opened.** `AXPress` on an `AXMenuBarItem` of a background app returns success and opens nothing — and the bar items measure 0×0 when the app is not frontmost. `AXPress` on an `AXMenuItem` *does* run the command with the menu closed and the app behind. So tapping a menu-bar title only marks it expanded for the next read, which lists its enabled items as `View › Scientific` (submenus flattened into the path). This keeps the Choice small: System Settings has 74 menu items, big apps hundreds.
- **Pop-up and menu buttons are opened for real, and an open menu is the control's `AXMenu` child.** A closed `AXPopUpButton` has no menu child at all; open, the menu measures 0×0 at the bottom of the screen while its items have real frames, so a read lists it before the frame check would prune it: region `Menú`, items as `Flavor › Mint` (control name › item). Tapping a pop-up opens it with `AXPress`, then `AXShowMenu`, then a click, each one waiting up to 600 ms for the child (1.5 s after a click) so a late menu is never opened twice; tapping it again sends `AXCancel` to the menu. `AXCancel` closes the menu only when one is open: with two stacked (opened twice), it answers success and both stay, which is why a second menu is refused (`menuAlreadyOpen`). Tapping an item presses it and the menu closes.
- **A toolbar button that shows a menu looks like any toolbar button.** Calculator's "Mode" and "Show Sidebar" are both `AXButton` with `AXPress` and `AXShowMenu` (every AppKit toolbar item advertises `AXShowMenu`, for customisation) and nothing else tells them apart. On "Mode", `AXPress` and `AXShowMenu` both succeed and open nothing; only a click opens it. So a toolbar button with `AXShowMenu` is pressed, and only if no menu appears and nothing in the window changes within 600 ms is it treated as a menu (`AXShowMenu`, then a click). A toolbar button whose effect takes longer than that would be clicked a second time.
- **A real click waits until it would land on the app, or is not sent.** Being frontmost is not enough: from a full-screen terminal with Calculator on the desktop Space, Calculator was frontmost at 133 ms, its window on screen at 245 ms and listed by AX at 546 ms; a click sent at ~280 ms fell into the Space animation and opened nothing. So `click` activates and waits up to 2 s until the topmost layer-0 window under the point belongs to the app and AX lists its windows, then 100 ms more. If that never happens it throws `notClickable` and sends nothing: a blind click lands on whatever covers the app — the user's terminal, in the case measured. With several windows the target one is raised (`AXRaise`) and the window under the point must not be *another* window AX lists for the app (a sheet, not listed, passes); a chosen window that closed surfaces as `windowGone`. Coordinate taps resolve the window the same way and fail with its error instead of clicking relative to a stale origin.
- **Reading back inside a row starts from its state before the press.** A press in a row that was already selected is verified only by the window changing, and `AXSelected` on a selected row is `notDelivered`, so the ladder goes on to the click instead of claiming success.
- **`toggle` waits once more before clicking.** `AXValue` writes the target state, but a click flips: if `AXPress` was taken with no visible effect, the driver polls again before the click, so a control that reacts late is not flipped twice.
- **`set_value` reads back over 600 ms**, and a number that lands on a nearby value (a slider rounding to its step) is `delivered`, not `noEffect`. Numbers take `0.5`, `0,5`, `1,000.5` or `1.000,5`; a lone `,` is a decimal point.
- **Windows on another Space are not listed by AX.** With the terminal full screen, Calculator had a window for the window server (off screen) and none in `AXWindows`; Finder with four windows elsewhere listed none of them. AX still hands out the app's focused and main window wherever it is, so reading falls back to it. The other windows are found through the window server (`CGWindowListCopyWindowInfo`: the app's titled windows on layer 0 that `AXWindows` lacks) and `CGSCopySpacesForWindows`, private, which tells them from inactive tabs: a tab is titled, off screen and missing from `AXWindows` too, but on no Space. They count towards `ambiguous_window` and `list_windows` marks them `[en otro escritorio]`; choosing one that is not the focused one fails with `window_on_other_space`. Titles need Screen Recording: without it nothing is found and only the focused window is read.
- **Bringing a window from another Space goes through the app's Window menu.** Measured on Chrome, with one window on the current Space and one elsewhere: `AXPress` on the second's item in the Window menu (menu closed, app behind) switched to its Space and focused it, and `AXWindows` listed it 491 ms later (0.8–0.9 s for the whole `bring_to_front`). `AXRaise` + `AXMain` + `activate()` on that window, reachable as the app's focused one, did not switch: activation went to the app's window on the current Space. The Window menu is taken as the menu-bar item before the last (Help), not by name, so the app's language does not matter; the item must carry the window's exact title. With no such item the app is only activated, which switches Space only when it has no window on the current one. A window on the current Space is raised (`AXRaise`, `AXMain`) and the app activated: 0.2 s from behind another app. It counts as in front when the app reports `AXFrontmost`, AX lists the window and it is the main or focused one; the system-wide `AXFocusedApplication` reads back nil from the MCP, so it is not used there.
- **Off-Space windows cannot be reached any other way.** `_AXUIElementCreateWithRemoteToken`, which builds an element from the app's pid and an element id, found Calculator's off-Space window (id 43, 1000 ids in 0.06 s) but none of Finder's four in a million ids (15 s): an element gets its id the first time an AX client asks for it, so a window nobody read is out of reach.
- **`select` reads the choice back from the control**: a pop-up's `AXValue`, or a menu button's title or identifier (Calculator: `Mode: scientific; unitConversion: false`). A menu item that runs a command shows nothing there, so a miss is `delivered`, not an error. Text the control already showed before the press (its own label, the previous choice) does not verify a substring match. An item press that leaves the menu open is `noEffect`: the menu is cancelled and the error says so. On a plain button `select` skips `AXPress`, which would run the button — but a toolbar button with `AXShowMenu` may still need the click (Calculator's "Mode"), and on a button without a menu ("Show Sidebar") that click runs it. That is detected (no menu, the window changed), reported as a `clic` step `delivered`, and makes `menu_did_not_open` not `retry_safe`. A menu that appears after the driver gave up is cancelled before the error.
- **An open menu has an item on screen.** `menu(of:)` and the reading require the `AXMenu` child to have at least one item with a non-empty frame, so a control that keeps a closed menu child does not read as always open.
- **Typing is `AXSelectedText`**, which inserts at the caret and takes any Unicode — the simulator's US-keyboard limit does not exist here. Erasing rewrites `AXValue`.
- **Return is a key event posted to the pid, not `AXConfirm`.** `AXConfirm` fires the field's `onSubmit` — but a field without `onSubmit` does nothing, while a real Return triggers the form's `.defaultAction` button. `CGEvent.postToPid` reaches the focused field with the app in the background and matched a real HID Return in every case measured.
- **Date pickers take `AXValue`.** Setting an `NSDate` on an `AXDateTimeArea` updates the SwiftUI binding, not just the control. `set_value` writes it from `yyyy-MM-dd HH:mm`, `yyyy-MM-dd` (keeping the time) or `HH:mm` (keeping the day), local time, and compares to the minute.
- **Text fields are not written through `AXValue`.** On a SwiftUI `TextField`, setting `AXValue` changes what the field shows and reads back, while the binding keeps the old string. `set_value` goes through the field editor instead — focus, `AXSelectedTextRange` over everything, `AXSelectedText` — which updates the binding, and falls back to `AXValue` if that is refused.
- **Password fields cannot be written or read through AX.** A SwiftUI `SecureField` (`AXSecureTextField`) answers success to `AXFocused`, `AXSelectedText` and `AXValue` and its binding never changes; its `AXValue` reads back empty. The driver never shows a password field's value in a reading anyway, and `set_value` on one reports `delivered` with a warning instead of `verified`. **Keyboard events do reach it**: `type_text` and `erase_text` on a password field post one key event per character (its Unicode string) or a Delete per character to the process, as `submit` posts Return. Measured on the onboarding's `SecureField`, with Calculator in front: `clave-ñ-prueba` reached the binding whole, and seven deletes left `clave-ñ`.
- **`toggle`** reads `AXValue` (0/1) before, then tries `AXPress`, `AXValue` and a click, each one confirmed by the value flipping. A checked radio button is refused: clicking it does not uncheck it.
- **Windows are identified by the window server's number** (`_AXUIElementGetWindow`, private but stable) plus the process start time (`sysctl` `p_starttime`), so a relaunched app that reuses a number is not taken for the same window. The same number picks the window ScreenCaptureKit captures, so two windows of one app with the same frame no longer get mixed up; a sheet still goes by frame. With `requireWindowChoice` (the MCP), two or more `AXStandardWindow`s that are not minimized and no choice made is `ambiguousWindow`; a focused `AXDialog`/`AXSystemDialog` of the app is read instead of the chosen window while it is up.
- **Scrolling moves the vertical `AXScrollBar`'s `AXValue` (0…1).** The `AXScrollDownByPage`/`UpByPage` actions fail (`-25205` / `-25204`), and a scroll-wheel `CGEvent` posted to the pid does nothing to a background app. A page is `0.8 × visible / (content − visible)` of the bar, with content height from the union of the content's frames. An area without a vertical scroll bar fits entirely and is not a candidate.
- **Launch activated, then hand focus back.** An app opened with `activates = false` that has never been frontmost has a window for AX but not for the window server: ScreenCaptureKit cannot see it. Being frontmost once is enough. `launch` waits for the window and re-activates whatever was in front. `-ApplePersistenceIgnoreState YES` stops window restoration; app-level state is the app's (Calculator still shows its last result).
- **Find the capture window by frame, restricted to the app.** System Settings' window belongs to the pane's extension (`com.apple.systempreferences.GeneralSettings`), so the owner can be the app's pid or a bundle id under the app's prefix — never anything else: two maximized windows share a frame, and an unrestricted match once returned Chrome's window for flowforge's.
- **Only windows on the current Space can be captured.** Off-Space windows reach ScreenCaptureKit with nonsense frames and do not match; System Settings captured off-Space comes back blank (so does `screencapture -l`). AX is unaffected — only the mirror and run screenshots fail, with `notCapturable`.
- **Two copies can share a bundle id** (the Xcode build in DerivedData and the one in `/Applications`, both running). `MacApp` is identified by its bundle URL; the driver reads, kills and relaunches that copy only, and `launch` opens that URL instead of asking Launch Services.
- **Never signal an app under the debugger.** Xcode intercepts the kill and leaves the app paused instead of dead, and every AX read then hangs to its timeout. `terminate` and `launch` check `P_TRACED` and refuse with `underDebugger`. Running the target from Xcode is the normal case, not an edge.
- `NSWorkspace.runningApplications` includes Device Hub with pid -1, which is not a process. The sidebar follows `didLaunch`/`didTerminateApplication`; those updates never clear the selection, because a relaunch removes the app from the list for a moment.
- A command-line binary that calls `SCScreenshotManager` asserts in `CGS_REQUIRE_INIT` unless it touches `NSApplication.shared` first. This only bites throwaway harnesses.
- Crash detection mirrors sim-use: once the app has been seen running, its absence comes back as `vanishedApps` with an empty screen rather than an error.

## Showing where the agent acts

`MacDriver` acts through Accessibility and never moves the cursor, so a tap on a background app is invisible. With the Fingertip menu-bar app running, `ScreenInspector.perform` sends an `OverlayEvent.pointer` over the `ActivityBeacon` socket before each tap or scroll: the element's frame in global screen coordinates (its bounds plus the window origin, `ScreenHierarchy.screenOrigin`). The app converts from Accessibility's top-left origin to AppKit's bottom-left one, picks the display containing the frame, and draws a ghost pointer in a click-through window there. Simulator actions send nothing: their points are not on this Mac's screen.
